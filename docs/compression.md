# 无损压缩与「带宽换算力」：可行性测量与路线

> 本文回答一个问题：**无损压缩能不能帮我们减少传输/内存带宽压力**，以及如果不能，
> 该用什么替代。全部数字都是本机（Loongson-3B6000 / LA664，12 物理核 + 24 逻辑核）
> 实测，测量脚本与陷阱都在文末，可复现。

## 1. 结论先说

1. **通用无损压缩在我们数据上的收益远比直觉小**：单次快照（内核一次调用吃的那
   6 个 f64 数组）最好只有 **1.22×**（zlib-6 + 字节平面）/ 1.15×（lzma 原生）；
   **轨迹**（64 帧，时间轴相关）也只有 **1.40×**。不是 2–4×。
2. **把它放进内核热路径不可行**：本机 zlib-6 解码只有 **0.37 GB/s**，而 RK4
   单线程内核消费 **3.3 GB/s**——差 9 倍。lz4/zstd 也一样（且这三个库在
   loongarch64 上没有 SIMD 路径，只会更慢）。
3. **「牺牲算力换带宽」的方向本身是对的**，但能换来带宽的不是通用压缩，而是三件
   已经被我们实测验证过的事：
   - **直接吃紧凑表示**：`lasx_dot_q4` 用 4-bit nibble 表示，带宽是 f32 的 1/8，
     实测比标量快 **11.4×**；
   - **重算代替存储**：融合内核 vs 用原语拼装，**2.8×**（28 MB 中间量从未落内存）；
   - **分块提高复用**：matmul 从 4 行×32 列改成 8 行×16 列，B 的流量 **−33%**
     （§5 的推算，逐位不变，尚未实现）。

## 2. 判定式：压缩什么时候能赢

必须先把两种场景分开，它们的判据完全不同：

**A. 链路上限场景**（网络、磁盘、跨进程传输）：数据要跨过一条慢链路。

```
收益 = 压缩比 r           解码只要快过链路速率即可（一般轻松满足）
```

此时 1.2–1.4× 是有意义的：1 Gbps 链路上 1.4× 就是少传 29% 的时间。

**B. 内核内场景**（数据已经在内存里，要省的是内存带宽）：压缩不减少"要处理多少
数据"，只把"从内存读"换成"从压缩形式解出来"。

```
原始：  时间 = B / C           （B 字节，内核消费速率 C 字节/秒）
压缩后：时间 = B / D           （解码速率 D 字节/秒；B/D ≫ B/(r·BW_mem)）
要赢：  D > C                 ← 压缩比 r 根本不出现
```

也就是说：**在内核里，压缩比几乎无关，解码速率必须超过内核自身的消费速率**。
本机的关键数字：

| 量 | 实测 |
|---|---|
| RK4 单线程消费速率 `C` | **3.3 GB/s**（12.6 MB 读 + 12.6 MB 写 / 7.55 ms） |
| 12 线程聚合 | **≈25 GB/s**（DRAM 上限，加线程不再涨） |
| zlib-6 解码 `D` | **0.37 GB/s** → 差 9 倍，出局 |
| lz4 / zstd 解码 | 本机无 loongarch64 SIMD 路径，只会更慢 |

**所以 B 场景要能成立，必须自己写 SIMD 解码器**（定长位平面打包 + 移位，
理论上能到几个 GB/s），而且要面对下面这个更致命的问题：**快照的压缩比只有 1.2×**，
即便解码无限快也只是 1.2×。这就是为什么 §5 的路线把 B 场景从"压缩"改成了
"数据流优化"。

## 3. 实测：能压多少

数据用仓库里的真实生成器（`cli/src/data.rs:states/velocities` 同构），
轨迹是把生成器相位每步推进一点点（帧间相关但不重复，模拟多步传播的输出）。
`byte-planes` 是字节平面切分（把每个元素的第 k 个字节连续排在一起，纯 SIMD
gather/scatter，不需要逐元素分支）。

| 数据集 | 大小 | raw+zlib6 | raw+lzma1 | planes+zlib6 | planes+lzma1 |
|---|---|---|---|---|---|
| 快照 6×f64（内核输入） | 0.8 MB | 0.957 | 0.872 | **0.822** | 0.812 |
| 轨迹 64 帧 × 6×f64 | 50.3 MB | 0.958 | 0.779 | 0.823 | **0.715** |
| 轨迹 + 帧间 XOR + planes | 50.3 MB | — | — | 0.855 | 0.750 |
| 随机 f32 值 | 0.26 MB | — | 0.915 | — | 0.816 |
| 真随机字节（探针自检） | 0.13 MB | 1.000 | 1.001 | — | — |

读法：

- 快照最好 **1.22×**；轨迹最好 **1.40×**（lzma+planes）。帧间 XOR 反而**没有**
  帮助（0.750 vs 0.715）——我们的轨迹每帧之间相关性不够强，而异或把高位也搅乱了。
- 随机 f32 也能压到 0.816：**浮点不是均匀字节**，指数位和符号位高度可预测。
  但这只是"少传 18%"，不是数量级。
- 真随机字节 1.000，说明探针本身没问题（第一版把 31 位切片当字节流，高比特恒 0，
  压出 0.878 = 7/8 的假象，已修）。

编码/解码速度（单核，本机）：

| 编解码器 | 比 | 编码 | 解码 |
|---|---|---|---|
| lz4 -1 | 0.518* | — | — |
| zstd -3 | 0.125* | — | — |
| zlib -6（进程内） | 0.693* | 0.06 GB/s | **0.37 GB/s** |
| lzma -1（进程内） | 0.111* | 0.03 GB/s | 0.09 GB/s |

\* 这一组是在"帧间复用同一数组"的**假数据**上测的，比例不可用，只用来读**速度**；
decode 速度后来用进程内调用复测（避免 subprocess pipe 干扰），结论不变：
**单核解码 0.1–0.4 GB/s 量级**。

## 4. 木桶：长板到底有多长

本机 RK4 J2 单步的算力占用（LASX f64 峰值按 46.6 GFLOP/s）：

| 口径 | 实测 | 占峰值 |
|---|---|---|
| 单线程 RK4 | ≈6.9 GFLOP/s | **≈15%** |
| 单线程内存消费 | 3.3 GB/s | 远低于 DRAM 上限 |
| 12 线程内存消费 | ≈25 GB/s | **DRAM 到顶** |

所以"削长板补短板"确实有空间（算力只用了 15%），但注意**短板随配置变**：

- **1 线程**：短板是**算力**（实测该内核受 `xvfdiv_d` 除法吞吐限制），此时"牺牲
  算力换带宽"是反的；
- **12 线程**：短板是**内存带宽**（DRAM 到顶），此时才轮到换。

而且换的工具必须是"**少搬字节**"，而不是"把字节压小再解开"——后者会把短板从
内存搬到解码器上（§2 的判定式）。

## 5. 路线

| 阶段 | 内容 | 判据（做到什么算成功） |
|---|---|---|
| **P0** | 本文：判定式 + 实测 + 反例登记 | 已完成 |
| **P1** | **无损容器**（可选模块，零依赖自研）：面向**存储/传输**的轨迹、检查点、跨进程/跨语言边界；字节平面 + 定长位平面打包 | 比 ≥ **1.3×**（目标 1.4×），解码 ≥ 链路速率；**明确不进内核热路径** |
| **P2** | **内核内的省带宽三件套**（这才是 B 场景的正解） | 见下 |
| P2.1 | matmul 改 8 行×16 列分块：B 流量 −33%、A 流量 +100%，总流量 −33%（f64 版 8×8：总流量 −20%）；**逐位一致**，无精度代价 | 256³ 多核加速比从 5.4× 提到 ≥7× |
| P2.2 | RK4 中间量的重算/融合（已有 2.8× 对照） | 把 6 数组工作集从"读+写 × N"压到更少遍 |
| P2.3 | 把 `dot_q4`/`dot_i8` 的"直接吃紧凑表示"推广到更多算子（**有精度代价，需授权**） | 明确每算子的精度-带宽曲线 |
| **P3** | 反例登记：**不做**"压缩→解压→算"的内核路径（本机解码 0.37 GB/s vs 消费 3.3 GB/s） | 除非自研 SIMD 解码 > 3.3 GB/s 且比 > 2×，否则不再评估 |

P2.1 是唯一"零风险、纯收益"的一项（逐位不变），建议作为下一步。

## 6. 测量方法与陷阱（可复现）

- 数据与生成器同构于 `cli/src/data.rs`；轨迹 = 每步推进生成器相位（`0.0013`/步）。
- 压缩比用 Python 进程内的 `zlib`(zlib-ng 1.3.1) / `lzma`，以及 `zstd`/`lz4` CLI。
- **两个坑**（第一版都踩了，记录以免复现）：
  1. **别把 31 位切片当字节流**：`(x >> 33) & 0xFFFFFFFF` 再取 `>> 24` 只剩 7 位，
     高比特恒 0，压出 0.878 = 7/8，看着像"压缩收益"其实是位宽损失；
  2. **别用 subprocess pipe 测编解码速度**：0.8 MB 数据被进程启动与管道往返淹没，
     测出来 0.2 GB/s 全是开销；要么用文件 + 大样本，要么进程内调用。
- `/tmp` 是 tmpfs（8 GB，已用 80%），文件 IO 不构成瓶颈。
