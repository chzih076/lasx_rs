## 1. LA664 原子操作丢失更新（平台勘误）

### 1.1 事实

**这是 CPU 的勘误，不是本库的缺陷。** 本库只是恰好命中了它最容易触发的形态。

| 项 | 内容 |
|---|---|
| 受影响核心 | **LA664**（3A6000 / 3C6000 / **3B6000**）；LA464（3A5000）不受影响 |
| 触发条件（三条**同时**满足） | ① 两个线程在**不同物理核**上；② 对**同一地址**做**无数据屏障**的原子操作；③ 至少一个线程在原子操作之间**插入内存读取** |
| 最强触发形态 | 条件③里的读是 **LASX 向量读（`xvld`）** —— 报告实测该形态近乎必现 |
| 不触发的形态 | LSX 的 `vld` 不触发；无内存读不触发；带数据屏障的 `_db` 变体**全条件 0%** |
| 受影响指令 | `amadd` / `amcas` / `ammax` / `amswap` 等**无屏障**变体；`am*_db.*` 免疫 |
| 修复（官方） | 固件置 **MCSR24（CSR `0xf0`）bit 13 = 1** |
| 原始报告 | `https://jia.je/hardware/2026/09/24/loongson-cpu-erratum/` |

### 1.2 本库的命中点（静态审计 + 编译产物双侧确认）

| 检查 | 结果 |
|---|---|
| 全库原子读改写（RMW）调用 | **8 处** |
| 生产路径里用什么序 | **只有 1 处 `Ordering::Relaxed`**：`src/pool/mod.rs` 的 `next_job.fetch_add`（动态分块派活） |
| 其余 7 处 | 3 处 `Ordering::Release`（`epoch` / `done`）、1 处 `compare_exchange(Release, …)`，以及 3 处**测试代码**（`#[cfg(test)]` 起于 1106 行，不进发布产物） |
| 是否同时满足三条件 | **是**：worker 分布在不同物理核；`next_job` 是同一地址且无屏障；每次抢到块后立刻执行 `run_block`（LASX 内核）⇒ 条件③成立 |
| 编译产物佐证（库本体） | `target/release/liblasx_rs.rlib` 反汇编：**裸 `amadd` 4 条**、`amadd_db` 54 条、`amswap_db` 28 条（反汇编有效性另由 89 种 `xv*` 助记符佐证） |

**后果**：`next_job` 丢一次自增 ⇒ 两个 worker 拿到同一个 `idx` ⇒ **同一个块算两遍、另一个块永远不算**。
对本库的矩阵乘/矩阵向量乘内核，这表现为**输出矩阵有一块没被写**——不报错、不崩溃、数值就是错的。

### 1.3 措施

| 措施 | 状态 | 代价 |
|---|---|---|
| ① 该内核若不需要动态负载均衡 ⇒ 走**静态分块**分支 | **首选**（那条路径本来零原子） | 无 |
| ② 保留动态分块 ⇒ 把该处 `Ordering::Relaxed` 改为 `AcqRel`（生成 `amadd_db`） | **已落地**（2026-10-03，`src/pool/mod.rs` 的 `next_job.fetch_add` 现为 `AcqRel`） | **实测无可测代价**，见下 |
| ③ 加"同输入跑两次必须逐位一致"的回归测试 | **已落地**：`parallel::tests::test_dynamic_scheduling_is_bitwise_reproducible`（768³ × 24 线程 × 3 组，走 `Pick::Dynamic`；0.04 s） | 极低 |

**当前 master 的状态**：②与③都已在代码里——**动态分块路径不再裸用 `amadd`**，且插入了能自动
发现该类问题的回归测试。因此 §1.6 说的"调用方无需为这条勘误做任何事"现在是**真的**。

**② 的实测（2026-10-03，本机）**：

> **口径**：下表的编译产物读数是**静态链接的可执行文件**（外挂基准 crate，把库链进去），
> 与 §1.2 表里的 `.rlib` 读数**不是同一个产物**，两组数字不可互相换算：
> `.rlib` 只含库本体（裸 `amadd` 4 条），可执行文件另含 `std` 与基准代码（16 条）。
> **能证明"改动精确落在该处"的是同一产物改动前后的差**，不是绝对值。

| 项 | 数据 |
|---|---|
| 编译产物差异（同一基准可执行文件，改前 → 改后） | `amadd` 16 → 15，`amadd_db` 127 → 128（**正好一条**） |
| 受影响路径 | 仅 `1024³ × 24 线程` 走 `Pick::Dynamic`（判据 `threads ≥ 20 && per_thread ≥ 32`） |
| A/B（背靠背交替，各 3 轮） | `Relaxed` 530.0 / 530.8 / 527.2 vs `_db` 534.9 / 524.9 / 529.7（GFLOP/s）⇒ **差异在 ±7% 噪声内** |
| 理论核对 | 1024³/24 线程 ⇒ 块长 12 行 ⇒ 约 86 个块 ⇒ **每 1260 万次乘加一道数据屏障**，与"测不出"一致 |

> **口径说明**：本机是**桌面**（有 Firefox / KDE / pipewire 等后台负载，`loadavg` 1–8 波动），
> 组内波动 ±7%。**跨时间引用旧基线会得到错误结论**——本文的 A/B 一律是背靠背交替，不引用历史读数。
> （这条不是理论洁癖：本次工作中曾用"半小时前的基线"与"当前修复态"比较，得出"有 10–15% 代价"的
> **错误结论**；同一时刻回滚态的重测显示机器整体已慢 12%，与本次改动无关。）

### 1.4 契约与"谁守"（按 §AGENTS.md 规则 5）

| 契约 | 谁守 | 违反的后果 |
|---|---|---|
| 生产路径不得对共享计数器做**无屏障** RMW | **只靠约定 + 一条回归测试**。类型系统不守、借用检查器不守、编译器不守（`Relaxed` 是完全合法的 Rust） | **静默错结果**（不是 UB） |
| 上述回归测试："同一输入跑两次，输出必须逐位相同" | 测试（建议进 CI） | 漏掉 ⇒ 该勘误类问题无法被自动发现 |

**为什么必须加那条回归测试**：本条勘误的失败模式是**静默且不可复现**的——丢一次自增不会当场报错，
只会在结果里体现为一块数据不对。**对比两次运行是唯一能在 CI 里自动发现它的办法**，
且成本极低（跑两次，逐位比）。

**本条勘误不在 §dev.md 的"例外清单"里**：例外清单管的是"我方主动选择了不同的数值路径"，
而这里是**平台给的外部风险**。两者性质不同，不合并。

### 1.5 验证方式（可复现）

触发与否**只能靠实测判断**，不能靠版本号推断（与 §3 的内核 CVE 不同）。

| 需要的东西 | 说明 |
|---|---|
| 最小复现器 | 两线程绑**不同物理核**（本机 `cpu0` 与 `cpu2`；`cpu0`/`cpu1` 是同核 SMT 兄弟，绑错测不出），各自在一个循环里交替执行 `xvld` 与 `amadd` |
| 判据 | 三个共享计数器在结束后必须**完全相等**（逻辑上增量相同），不等即为丢更新 |
| 对照 | 四组：`xvld`+`amadd`（应触发）/ `vld`+`amadd`（应 0）/ 无读+`amadd`（应 0）/ `xvld`+`amadd_db`（应 0） |
| 本机结果 | 修复前 **45/100 触发**；修复后 **0/200**；三组对照全部 0 |

**一个实测教训**（值得记，因为它和本库的验证纪律冲突）：**用 C 写复现器时，编译器的指令调度会
把 `xvld` 与 `amadd` 排开**，导致三代 C 版本全部"0/30 不触发"——**而代码看起来完全正确**。
换成手写汇编精确排布后一次命中。**"我写了 LASX 读 + 原子操作"不等于"它们真的交错"。**

### 1.6 与 `docs/ops.md` 的关系

**调用方无需为这条勘误做任何事**：命中点在库内部，且无论走静态还是动态分块，修复都在库侧完成。
调用方若需自证，用 §1.5 的复现器；若需在**受影响且未修**的机器上临时规避，办法是把动态分块关掉
（走静态分支）——但那是根治，不是缓解。

## 2. 分发时的含义：不能依赖固件修复

| 事实 | 含义 |
|---|---|
| 官方修复是**固件**级的（MCSR24 bit 13） | 我方**无法保证**目标机器已升级固件；部分型号的固件版本尚未发布 |
| 该位**不持久**：CSR 随复位回到 0 | 已升级的机器重启后可能回到未修状态，除非固件自身置位 |
| 可以通过内核模块在运行时置位 | 本机已用此路径验证有效（24 核全部生效、重启后失效），但**这属于部署方的事，不是库的事** |

**⇒ 结论：库侧必须自带 `_db`，不能假设"对方机器已经修好"。** 这也是 §1.3 措施②不退让的理由——
它的代价测不出来（§1.3），而它买到的是**在任何机器上都成立**。

**另一条**：`Arc` 等标准库类型的引用计数也用无屏障 `amadd`，**我方无法修改**。
触发窗口窄（建池/拆池而非热循环），风险低于 `next_job`，但**这条无法靠本库消除**，只能靠固件。

## 3. 平台支持状态：内核分支生命周期

**本节不是本库的缺陷，但它决定"这台机器上还能指望什么"。**

| 项 | 2026-10-03 观测 |
|---|---|
| 本机内核 | `7.1.13-aosc-main-4k`（AOSC OS 13.3.1） |
| kernel.org 的维护列表 | `5.10 / 5.15 / 6.1 / 6.6 / 6.12 / 6.18 / 7.2 / 7.3` —— **7.1 不在其中** |
| 7.1 系列的最后一个版本 | `7.1.13`（即本机所用），**之后没有 7.1.14** |
| 当前 mainline / stable | `7.3-rc5` / `7.2.8` |

**对维护的含义**：

1. **已修的洞不必担心**：本机实测两条 2026 年的高危提权洞——
   GhostLock（`CVE-2026-43499`，影响范围 `v2.6.39-rc1`→`v7.1-rc1`）与
   Route of Root（`CVE-2026-43501`，影响范围 `v5.7-rc1`→`v7.1-rc1`）——
   **修复点都落在 `v7.1-rc1`，本机 7.1.13 已包含**。
2. **要担心的是下一批**：修复点落在 `7.2.x` 的洞**不会 backport 到 7.1**。
   2026-10-03 观测到至少 5 条属此类（BPF JIT / BPF refcount / xsk / iris / jbd2），
   其中 BPF 两条被 `kernel.unprivileged_bpf_disabled=2` 缓解，iris 与 LoongArch 无关。
3. **趋势**：2026 年的内核漏洞中有相当比例来自**自动化工具对老旧代码的系统性扫描**
   （GhostLock 由 NebuSec 的 VEGA 工具在 2026-02 发现）。这意味着**"没被找过"不等于"没有"**，
   控制手段只有一条：**缩短每个洞的存活窗口**。

**这是部署方的事，不是库的事**——本库不依赖内核版本，只依赖 ISA（LASX/LSX）。
但记录在此，因为**维护节奏**（什么时候该重测性能、什么时候该复核勘误是否仍然需要规避）与它相关。

## 4. 消费 ONNX 契约引出的实现缺口

**背景**：模型的推理契约由 ONNX 图给出（已验证与参考实现数值一致，最大绝对误差 1.9e-06）。
下表中"图上数量"指该 ONNX 图里的节点数（1228 节点 / 29 种算子）。

| ONNX 图上的算子 | 数量 | 本库现状 | 缺口 |
|---|---|---|---|
| `MatMul` / `Gemm` | 96 / 1 | ✅ 已有 | — |
| `Softmax` | 12 | ✅ `softmax_rows`（`mask` + `scale` 参数齐备） | — |
| `Erf`（GELU 的一部分） | 12 | ✅ `gelu_erf` | — |
| `Pow`/`ReduceMean`/`Sqrt`（归一化的一部分） | 各 32 | ✅ `rms_norm` 一次调用覆盖 | — |
| **`LayerNormalization`** | **17** | ✅ **已实现**（2026-10-03）：`api::layer_norm` / `layer_norm_into`、`ops::layer_norm`（契约 `docs/ops.md` §2.16；与 `rms_norm` 同一行归约骨架，差别是减均值 + 偏置 β） | — |
| **`Gather`**（ONNX 算子：词/段/位置嵌入） | 34 | ❌ **缺**（注意 `src/plan.rs` 有个私有 `gather_columns`，是矩阵列搬运、与本算子无关） | 需要实现（按 id 取行） |

**两个缺口的现状**：

1. **`LayerNormalization`**：ONNX 图上 17 处 = 嵌入层 1 处 + 前 8 层每层 2 处。
   若采纳"全 12 层统一改用 `x/rms·γ + β`"（见 `docs/dev.md` 的相关设计小节），
   **这个缺口会消失**——库侧只需要一套归一化。该改动需要重训，**不在此文档的范围内**，
   但它是"少一个算子"和"多一个算子"的分界，记录在此。
2. **`Gather`**：难点不在实现（按 id 拷 384 个浮点），而在**要不要支持 int8 嵌入表**——
   词表 250037×384 的 fp32 表是 **384 MB**，int8 后 96 MB，**这是模型体积的大头**。
   这是一个设计决策，不是纯实现任务。

### 4.1 融合会减少可对拍的点位（这条与 §AGENTS.md 规则 4 冲突，需要正视）

| 侧 | 可观测点 |
|---|---|
| ONNX 图 | **1228 个节点**，每个节点后的中间张量都可读 |
| 本库执行 | 约 **180 次内核调用** |

映射是**多对一**的：

```text
Pow + ReduceMean + Add + Sqrt + Div + Mul   （6 个节点）  →  rms_norm   （1 次调用）
Erf + Mul + Add                             （3 个节点）  →  gelu_erf   （1 次调用）
```

**⇒ 融合之后，ONNX 中间张量对应的位置在本库里根本不存在。**

**后果**：规则 4 要求的"逐层对拍"在**融合边界上无法执行**——不是"漏测了"，是**物理上没有那个测点**。

**决策（2026-10-03）：只在层边界对拍；算子级定位由本库已有的算子测试承担。**
（三条出路的代价见下，决策依据在"为什么"里。）

| 层 | 测什么 | 谁提供 |
|---|---|---|
| ONNX 参考 | 1228 个节点，每个中间张量可读 | 消费侧（本仓库外） |
| **对拍点** | **层边界**（嵌入后、前 8 层每层的两处、分类头前）≈ **14 点** | 调用方持有激活缓冲即天然可观测；**本库侧无需新代码** |
| **算子级定位** | 每个融合算子**自己的**测试（对照独立参考） | 本库 `ops` 层：`softmax_rows` 4、`rms_norm` 4、`gelu_erf`/`gelu_quick`/`silu` 各 3、`rope` 6、`dot_f16` 5、`matmul` 3 = **31 个**（其中 **26 个** ops 文件显式对照独立参考） |

**为什么这样切**：

1. **分工不同**：层边界查的是**接线**（转置 / scale / mask 接错、算子顺序错），算子测试查的是
   **算子本身**。融合让"ONNX 中间张量"消失，受影响的只是**接线层**的可观测点；而接线错误必然
   在层边界显形 ⇒ 层边界对"接线"是充分粒度，算子内部错误由算子测试抓，两条链合起来完整。
2. **未融合调试路径的成本不只是代码**：它还必须证明"未融合 ≡ 融合"（否则出现差异时无法判断
   哪一侧错），这等于给验证体系再加一条硬承诺；买到的却是**与已有算子测试重复**的能力。
3. 消费侧已用**端到端最大绝对误差 1.9e-06**（对 ONNX 参考）验过融合路径一遍 ⇒ 总误差量级已知，
   剩下要防的是**回归**，而回归用"14 个层边界点 + 31 个算子测试"足够。

**触发条件（什么时候回头做"未融合调试路径"）**：真出现一次不一致，且
**层边界全对 + 算子测试全绿，而端到端指标仍超差**——那时它的形态才是立项依据
（**记下那次的具体形态再立项**，不要预先养一条调试路径）。

**谁守什么**：对拍点数与容差由**消费侧的验证脚本**守（本仓库外，S 级：它决定"能不能发现"）；
那 31 个算子测试由 `cargo test` 守；**"融合减少了可对拍点位"这件事本身由本节守**——
写在这里，避免后人以为本库的点位与 ONNX 一一对应。

<summary>当初列出的三条出路（保留作为备查）</summary>

| 方案 | 代价 |
|---|---|
| 让本库提供**未融合的调试路径**（慢，但点位与 ONNX 一一对应） | 多一套代码路径，且它本身也需要位精确验证（还要证明"未融合 ≡ 融合"） |
| 只在**层边界**对拍（12 个点 + 首末层） | 粒度粗一档；块内错误无法定位到具体算子——**由算子测试补上**（本决策选它） |
| 两条都做：层边界进 CI，未融合路径做定位工具 | 成本最高；"发现不一致 → 定位到算子"这条链完整，但维护两套验证面 |

</details>

## 5. 承诺边界待重新划定的项

**本节的共同点**：它们**不是实现难度问题，是"承诺什么"的问题**。
按 §AGENTS.md 规则 3，**动手前先在 `docs/dev.md` 记一笔**。

### 5.1 int8 路径：「位精确」跟谁一致？

| 路径 | 现状的承诺 | 问题 |
|---|---|---|
| fp32 | **位精确**（`docs/ops.md §2.5`），对照物明确 | 无 |
| int8 | **未定义** | 跟 fp32 比不可能一致（量化本身有损）；跟另一个 int8 实现比则**没有天然对照组** |

**已有的实测依据**（来自 `docs/dev.md` 的相关小节）：权重 per-channel 量化近乎无损；
激活 **per-tensor 93.4% vs per-token 96.1%**——**per-token 是前提而非优化项**。

**待决策**：int8 路径**端到端（模型级）**的验收标准写成**误差上界**（而非位精确），
并明确上界的口径（逐元素相对误差？还是端到端指标？）。
> **单层的口径已经定死了**（2026-10-03，`docs/ops.md` §2.15）：`max|Y_q − Y| / max|Y| ≤ 1e-2`
> （对 f64 参考；实测最坏 6.05e-3，f32 对照 ~1.4e-6），由
> `api::tests::test_int8_pipeline_relative_error_is_bounded` 守（3 形状 × 3 种子）。
> **仍待定的只有"整模型"那一档**：要么按层数开方推（12 层 ≈ 2.1e-2），要么在真模型上端到端实测。
> **算子级已经有标准**（`docs/ops.md` §2.12–§2.14）：位精确 = 同一算子的向量/标量路径
> **逐位一致**、整数累加精确、量化误差 ≤ `scale/2`（都有测试守着）。
> 缺的是**跨算子叠加后的端到端口径**——这一条在写下来之前，int8 的**模型级**承诺没有标准。

### 5.2 反向传播：为谁做？

**这一项尚未立项。** 记录在此，因为它会反向决定库的结构（是否需要保留中间量、是否需要可微路径）。

| 动机 | 评估 |
|---|---|
| 端侧微调（数据不出本地） | 与库的定位一致；但**模型要小、算子集要固定** |
| 可微仿真 / 科学 ML | 本库已有 `rk4_j2_step_batch` / `ballistic_step` / `quat_*`，这些算子的反向是**手推的**，与通用自动微分无关 |
| 通用训练框架 | **不建议**——那是另一个量级的目标，且与"零依赖 + 位精确"的现有约束冲突 |

**一条已知的硬冲突**：反向传播天然是**归约的海洋**（对 batch / 序列 / 通道）。
并行归约要么固定归约树（确定性、位精确、慢），要么用原子（快、**每次结果不同**）。
**而"位精确"是本库的硬承诺** ⇒ 若做反向，**只能走确定性归约**。

**注意这条冲突在 LA664 上不是"二选一"**：§1 的勘误已经把原子那条路在硬件层面变得更贵
（要用 `_db`），所以两个约束指向同一个结论——**确定性归约**。

### 5.3 本节的执行顺序建议

```text
1. 先划 int8 的承诺边界（它已经在用，只是标准未写）      ← ✅ 已办（单层口径见 docs/ops.md §2.15）
2. 再决定 §4.1 的对拍粒度（它决定验证能力）              ← ✅ 已办（选"层边界 + 算子测试"，见 §4.1）
3. 最后才评估 §5.2（它是否立项取决于前两项的结论）        ← 未办（反向传播，纯新增、成本最大）
```

**理由**：①②都是**已经在发生**的事（int8 有代码、ONNX 有契约），只是标准没写；
③是纯新增，且成本最大。**把已经发生的事的标准补齐，优先于开新战场。**
