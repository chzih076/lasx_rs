# lasx_rs 平台约束与支持状态

> 面向维护者与二次开发者：记录**外部给定**的约束（硬件勘误、平台支持状态、外部契约引出的缺口），
> 以及它们对"能不能用/怎么验证"的影响。设计与性能见 `docs/dev.md`；算子契约见 `docs/ops.md`。

## 1. LA664 原子操作丢失更新（平台勘误）

### 1.1 事实

**这是 CPU 的勘误，不是本库的缺陷**；本库只是恰好命中了它最易触发的形态。

| 项 | 内容 |
|---|---|
| 受影响核心 | **LA664**（3A6000 / 3C6000 / **3B6000**）；LA464（3A5000）不受影响 |
| 触发条件（三条**同时**满足） | ① 两个线程在**不同物理核**；② 对**同一地址**做**无数据屏障**的原子操作；③ 至少一个线程在原子操作之间**插入内存读取** |
| 最强触发形态 | 条件③的读是 **LASX 向量读（`xvld`）**——近乎必现 |
| 不触发的形态 | LSX `vld`；无内存读；带数据屏障的 `_db` 变体（全条件 0%） |
| 受影响指令 | `amadd`/`amcas`/`ammax`/`amswap` 等**无屏障**变体；`am*_db.*` 免疫 |
| 官方修复 | 固件置 MCSR24（CSR `0xf0`）bit 13 = 1 |
| 原始报告 | `https://jia.je/hardware/2026/09/24/loongson-cpu-erratum/` |

### 1.2 本库的命中点（静态审计 + 编译产物双侧确认）

| 检查 | 结果 |
|---|---|
| 全库原子读改写（RMW） | **8 处** |
| 生产路径的序 | 仅 **1 处 `Relaxed`**：`src/pool/mod.rs` 的 `next_job.fetch_add`（动态分块派活）；其余 7 处为 `Release`/`AcqRel`/测试代码 |
| 是否同时满足三条件 | **是**：worker 分布在不同物理核、`next_job` 同地址无屏障、抢到块后立刻跑 LASX 内核（条件③成立） |
| 编译产物佐证 | `.rlib` 反汇编：裸 `amadd` 4 条、`amadd_db` 54 条、`amswap_db` 28 条 |

**后果（若命中）**：`next_job` 丢一次自增 ⇒ 两个 worker 拿到同一块、另一块永远不算 ⇒ 输出矩阵**有一块没写**，
不报错、不崩溃、数值错。

### 1.3 措施（均已落地）

| 措施 | 状态 | 代价 |
|---|---|---|
| 无需动态负载均衡的内核走**静态分块** | 首选（该路径零原子） | 无 |
| 动态分块处 `Ordered::Relaxed` → **`AcqRel`**（生成 `amadd_db`） | 已落地（2026-10-03，`src/pool/mod.rs`） | **实测无可测代价** |
| "同输入跑两次必须逐位一致"回归测试 | 已落地：`parallel::tests::test_dynamic_scheduling_is_bitwise_reproducible`（768³ × 24 线程 × 3 组，0.04 s） | 极低 |

- 实测（背靠背交替 A/B，1024³ × 24 线程走 `Pick::Dynamic`）：`Relaxed` 530.0/530.8/527.2 vs `_db` 534.9/524.9/529.7 GFLOP/s
  ⇒ 差异在 ±7% 噪声内；理论上约每 1260 万次乘加一道屏障，与"测不出"一致。
- **当前状态**：动态分块路径不再裸用 `amadd`，且有回归测试守着 ⇒ **调用方无需为这条勘误做任何事**；
  但**同输入双跑逐位一致**的测试是发现这类问题的手段（漏掉就无法自动发现）。

### 1.4 契约与"谁守"

| 契约 | 谁守 | 违反后果 |
|---|---|---|
| 生产路径不得对共享计数器做**无屏障** RMW | **只靠约定 + 一条回归测试**（类型/借用检查器/编译器都不守） | **静默错结果**（不是 UB） |
| 同输入双跑逐位一致 | 测试（建议进 CI） | 勘误类问题无法自动发现 |

## 2. 平台支持状态：内核分支生命周期

> 这不是本库的缺陷，但它决定"这台机器上还能指望什么"。

| 项 | 观测（2026-10-03） |
|---|---|
| 本机内核 | `7.1.13-aosc-main-4k`（AOSC OS 13.3.1） |
| kernel.org 维护列表 | `5.10 / 5.15 / 6.1 / 6.6 / 6.12 / 6.18 / 7.2 / 7.3`——**7.1 不在其中** |
| 7.1 最后版本 | `7.1.13`（本机所用），之后无 `7.1.14` |
| mainline / stable | `7.3-rc5` / `7.2.8` |

对维护的含义：

1. **已修的洞不必担心**：2026 年两条高危提权洞（GhostLock `CVE-2026-43499`、Route of Root `CVE-2026-43501`）
   修复点都在 `v7.1-rc1`，本机 7.1.13 已包含。
2. **要担心下一批**：修复点落在 `7.2.x` 的洞不会 backport 到 7.1（2026-10-03 观测到至少 5 条：BPF JIT/BPF refcount/xsk/iris/jbd2，
   其中 BPF 两条由 `unprivileged_bpf_disabled=2` 缓解）。
3. **趋势**：相当比例漏洞来自对老旧代码的自动化扫描 ⇒ "没被找过 ≠ 没有"；唯一控制手段是**缩短每个洞的存活窗口**。
4. **这是部署方的事**：本库不依赖内核版本，只依赖 ISA（LASX/LSX）；但维护节奏（何时重测性能/复核勘误规避）与它相关。

## 3. 消费 ONNX 契约引出的实现缺口

**背景**：推理契约由 ONNX 图给出（已验证与参考实现数值一致，最大绝对误差 **1.9e-06**）；下表"数量"指 ONNX 图节点数（1228 节点 / 29 种算子）。

| ONNX 算子 | 数量 | 本库现状 | 缺口 |
|---|---|---|---|
| `MatMul` / `Gemm` | 96 / 1 | ✅ 已有 | — |
| `Softmax` | 12 | ✅ `softmax_rows`（mask+scale 齐备） | — |
| `Erf`（GELU 一部分） | 12 | ✅ `gelu_erf` | — |
| `Pow`/`ReduceMean`/`Sqrt` | 各 32 | ✅ `rms_norm` 一次调用覆盖 | — |
| `LayerNormalization` | 17 | ✅ 已实现（`layer_norm`，与 `rms_norm` 同行归约骨架，差减均值 + β） | — |
| `Gather`（词/段/位置嵌入） | 34 | ✅ 已实现（`gather_rows` / `gather_rows_i8`） | "表存 f32 还是 int8"由消费侧决定（见 3.2） |

### 3.1 融合会减少可对拍的点位（与"逐层对拍"要求的冲突）

| 侧 | 可观测点 |
|---|---|
| ONNX 图 | **1228 个节点**，每个节点后的中间张量都可读 |
| 本库执行 | 约 **180 次内核调用** |

映射是**多对一**（如 `Pow+ReduceMean+Add+Sqrt+Div+Mul` 6 节点 → `rms_norm` 1 次调用；`Erf+Mul+Add` → `gelu_erf` 1 次调用）
⇒ **融合之后，ONNX 中间张量在本库没有对应测点**——不是漏测，是物理上没有那个点。

**决策（2026-10-03）：只在层边界对拍；算子级定位由本库算子测试承担。**

| 层 | 测什么 | 谁提供 |
|---|---|---|
| ONNX 参考 | 1228 节点、每节点中间张量可读 | 消费侧（仓外） |
| **对拍点** | **层边界**（嵌入后、前 8 层每层两处、分类头前）≈ **14 点** | 调用方持有激活缓冲天然可观测；本库无需新代码 |
| **算子级定位** | 每个融合算子自己的测试（对照独立参考） | 本库 `ops` 层 31 个算子测试（26 个 ops 文件显式对照独立参考） |

理由：① 层边界查**接线**（转置/scale/mask 接错、顺序错），算子测试查**算子本身**，两条链合起来完整；
② 未融合调试路径必须额外证明"未融合 ≡ 融合"，成本高于收益且与已有算子测试重复；
③ 消费侧端到端 1.9e-06 已验过融合路径一遍，剩下要防的是回归，14 点 + 31 测试足够。

**触发回头做未融合路径的条件**：真出现一次不一致，且**层边界全对 + 算子测试全绿，而端到端指标仍超差**——
记下那次的具体形态再立项，不要预先维护调试路径。

### 3.2 `Gather` 与 int8 嵌入表：决策

**尺寸事实**（词表 250037 × 384）：fp32 表 **384 MB**（模型体积大头）；int8 表 **96 MB**（4× 小，per-row scale 另加约 1 MB）；
每次前向取用约 **288 KB**（192 行 × 1.5 KB = 表的 **0.08%**）⇒ **gather 带宽与表体积无关，只与 `batch × seq` 有关**。

**决策：库侧提供两种取行口径，嵌入表是否 int8 由消费侧决定**：
`gather_rows`（f32 行拷贝）/ `gather_rows_i8`（行拷贝 + 每行 scale 乘 = 取行 + 反量化），都只做内存搬运、不引入新数值语义。
