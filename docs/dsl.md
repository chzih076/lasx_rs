## 1. 四层架构与范围裁决

### 1.1 分层

| 层 | 职责 | 宏 | 状态 |
|---|---|---|---|
| **① 原语宏** | 一次调用 = **一条已实证的数值路径**；只做"点名调用 + 形状进类型"，不做重写 | `matmul!`、`dot!`、`gemv!` | ✅ 已落地 |
| | | `sum!`（单操作数归约） | ❌ **缺**（`lasx_sum` 只有 FFI/`api` 入口） |
| | | `exp!` / `sin!` / `cos!`（类型化逐元素） | ❌ **缺**（本阶段铺垫对象，见 §6.1） |
| | | `sum_range!` / `integral!`（索引空间与带权求和） | ❌ **缺**（本阶段铺垫对象，见 §6.2） |
| **② 变换宏** | **数学结构的重写**（等距递推、可分离核、Toeplitz/卷积、蝶形）——**DSL 的价值中心** | `laplace!`、`fourier!`、`conv!`、`fft!` | **草案**（宏名尚不存在；库内已有等价的显式入口，见 §1.2） |
| **③ 领域宏** | 某学科的标准流程 = 若干变换/原语的固定组合 | `transfer_function!` | **草案（合理，未实现）** |
| | | `stability!` | ❌ **不做成 DSL 语法，只给配方**（见 §1.2） |
| **④ 应用宏** | 整个产品级流程 | `orbit_propagate!`、`rocket_sim!` | ❌ **明确不做**（理由见 §1.2） |

> 关于 `sum!` 的现状说明（避免歧义）：`dot!` 已覆盖 `dot`/`dot_f64` 两种点积，但 **`sum` 这类
> "单操作数归约"缺句式** ⇒ `sum!` 是**缺口**，与 `docs/dev.md` §19.13 的 G1 行一致
> （那里登记的正是"标量输出的归约"这项原语）。

### 1.2 逐层裁决与理由

**① 原语宏：只做"点名调用"**。原语层的契约是"与库内同名入口逐位（或按 §4 登记的等价类）一致"，
所以它**不承担重写**；形状进类型、参数显式，用户写什么就调什么。已有三个宏的规则与诊断在
`docs/dev.md` §19.8、§19.13；缺的三类见 §6。

**② 变换宏：重写住这一层**。变换宏只负责**认出数学结构并选择正确的原语序列**：

- `laplace!` / `fourier!` 的形态是"在索引空间上对 `f(t_i)·kernel(θ_j·t_i)` 求和"，
  下降成 `integral!`，再下降成 `matmul!`（核矩阵 + 一次矩阵乘）。这条路**库内已经走通**
  （`laplace_batch_*` 把 `F(s) = ∫₀^∞ f(t)e^{−st}dt` 离散成两条实矩阵乘，见 `docs/ops.md` §9.0；
  复数版表面见 `docs/ops.md` §9.07）；**宏层要做的只是把这段已经实测的调用暴露成语法**。
- 收益必须来自**结构**而不是"宏"本身：等距递推这一条重写实测快 5.1×（`docs/ops.md` §9.10），
  真交替 A/B 为 −43.5%（小 `NB`）/−59.0%（大 `NB`）（`docs/ops.md` §9.10.1）。
- `conv!` / `fft!` 属于本层，但**下降形态与 `laplace!`/`fourier!` 不同**：卷积的自然形态是
  **Toeplitz 矩阵乘**（可复用 `matmul!`），FFT 是**蝶形**（不是矩阵乘）。⇒ **这两条的下降目标、
  等价类与守卫尚未裁决**，落地前必须按 §2.2 补齐登记；本文不替它们编方案。

**③ 领域宏：`transfer_function!` 合理；`stability!` 只给配方**。

- `transfer_function!` 合理，因为它**是**"若干变换/原语的固定组合"（`L{y} = H(s)·L{u}` ⇒
  一次 `laplace!` + 逐节点复数乘 + 一次逆变换），组合方式固定、形状可编译期定、且每一步都已经
  有库内实质（`docs/ops.md` §9.0/§9.05/§9.08）。它落地时**仍然遵守本文的分工纪律**：
  宏只转发，判据在库内。
- `stability!` **不做成 DSL 语法**：稳定性判定是**特征值问题**（极点位置/奇异值/根轨迹），
  DSL 的原语面是"矩阵乘 + 逐元素 + 归约"，**没有特征值求解这条路**；把它做成宏会让宏层去实现
  一套与数值内核无关的算法。⇒ **只给"配方"**：用已有 `matmul!`/形状层组装判据矩阵，
  特征值求解调用**外部例程或下游自有实现**（本库不提供）。若将来要做，它应当是**库内新算子**
  （有实测与契约）之后的事，不是宏层的语法。

**④ 应用宏：明确不做**——**框架陷阱**。宏系统一旦按"应用"命名（`orbit_propagate!`、
`rocket_sim!`），就会在**没有产品驱动**的情况下，在宏层里长出一个**没人用的物理引擎**：
时间步规则、坐标系与历元、摄动模型、轨道根数约定都是**产品语义**，不是库语义；把它们固化进库
意味着库要为某个产品的选择背书、并跟着产品的每次改动走。⇒ **正确位置是下游产品代码**
（例如 loong-sci 侧的组合调用），库只提供可组合的原语/变换/领域宏。

> **什么时候重开**（判据，避免"永远不做"变成"没想过"）：出现**两个以上独立下游**各自要同一套
> 端到端流程，且该流程的每一步都已在库里可组合 ⇒ 那时应把它固化成**领域宏或示例**，
> **仍然不是应用宏**。

## 2. 下降链与三条纪律

### 2.1 下降链（目标形态）

```text
laplace! / fourier!                 ← ② 变换宏：认出数学结构、选核、选路
        ↓
integral! / sum_range!              ← ① 索引空间与带权求和
        ↓
matmul! / exp! / sin! / cos!        ← ① 原语宏：点名已实证的内核路径
        ↓
rustc / LLVM                        ← 微观：向量化 / 展开 / 调度（结构重写后的常规形状）
        ↓
LASX 手写内核（“降级目标库”）        ← 只有 LLVM 做不到的形状才落到这里
```

- 层与层之间传递的是**形状进类型**的缓冲，因此衔接是编译期检查的（草案见 §6）。
- **现状：只有 `matmul! → rustc/LLVM 或 LASX` 这一段已落地**（`docs/ops.md` §9.0 的拉普拉斯 = 两条实乘，
  库内入口 `laplace::laplace_batch_*`）。`laplace!` 这样的**宏名尚不存在**——本阶段的目标是把
  上半段接上，**不是**新写数值路径。
- 为什么最后一层是"降级目标库"而不是"全部委派 LLVM"：委派到位率实测有硬边界，见 §5。

### 2.2 每条下降边必须带的三件套

**每条边都要声明这三件事，缺一不可**（本文把它们叫"三条纪律"）：

1. **等价类声明**：这条边是**逐位类**还是**容差类**（容差必须给**界**与**适用范围**）。
   登记在 §4；没有登记的边**不许进默认路径**。
2. **守卫 + 回退**：改写只在判据内生效；判据外**逐行/逐元素回退**到默认路径（位精确/libm），
   并把"发生过回退"**如实返回**给调用方（`all_safe=false` 这类返回值是既有形态）。
3. **认不出就不改写**：模式不匹配 ⇒ **完全不改**（`Rewrite::None`），**绝不猜**。
   负例必须有测试（`docs/dev.md` §9.5.1 的 `negative_non_isometric_or_nonlinear` 是样板）。

**目标契约（按边登记，未落地项标 ⏳）**：

| 下降边 | 等价类（目标） | 守卫 + 回退 | 认不出 ⇒ |
|---|---|---|---|
| `laplace!`/`fourier!` → `integral!` | 逐位（前端不改数值：同一 `s` 节点、同一权重、同一分平面） | 权重不适用（`N < 3` 或 `N` 偶数）⇒ **整段回退梯形**并如实标出（`docs/ops.md` §9.0） | 核不是"逐元素核 × 求和"⇒ 不降级 |
| `integral!` → `matmul!` | 逐位（同一累加次序；参考 = 行切版本） | 形状/布局不匹配 ⇒ 编译错误（类型系统守），不生成退化的替代路径 | 被求和项**不可分离**（不能写成"核矩阵 × 向量"）⇒ 不降级 |
| `integral!` → 逐元素 + 等距递推（**opt-in**） | **容差**（界见 §4 的 E3） | `recurrence_safe` **逐行**守卫；不安全的行**逐行回退 libm**，返回 `all_safe=false` | `StepKind::Varies` 或参数非线性 ⇒ `Rewrite::None` |
| `matmul!` → 库内内核（含 plan 复用形态） | **逐位** | 形状由类型系统守 | —（原语层无重写） |

## 3. 分工纪律（已裁决）：宏只解析转发、判据唯一在库内

**裁决**：

- **宏侧只做"解析 + 转发"**：把 DSL 表达式降成**描述符**，并发出对**库内入口**的调用；
  **不实现**"能不能重写 / 安不安全 / 该走哪条路"的任何判据。
- **判据唯一在库内**：`src/rewrite.rs::plan()`（识别与判定）与 `laplace::recurrence_safe`
  （安全区）是**唯一**的判据来源；宏发出的代码在 `Rewrite::Recurrence` 时调用库内已落地的
  `laplace_batch_{f32,f64}_recurrence`（内部 = 同源守卫 + 逐行回退 libm）——
  这就是 `rewrite::GENERATION_VIA_LIBRARY_ENTRY` 记录的那条路径。
- **原因（结构性，不是偏好）**：`lasx_rs` 依赖 `lasx_rs_macros`（proc-macro，见根 `Cargo.toml`），
  **反向依赖成环** ⇒ 宏 crate **不能**在展开期调用 `lasx_rs`。若把判据写进宏，就会得到
  **两份语义**（宏一份、库一份），两份迟早漂移——这是长期隐患，不是一次性成本。
- **微观交给 rustc**：重写后的循环要发成**编译器友好的形状**（迭代器链 / `chunks_exact` /
  `zip` / `fold` / 定长数组 + const generics / `mul_add`），**不要手写**这些常规形状的向量化。
  依据：惯用形状到手写内核的到位率实测 92%（`docs/dev.md` §9.5.4），且三变体同序逐位一致。

**已经提前钉住的锚点**（这条纪律不是纸面约定）：

- `#[fast_trig]` 已注册为**无操作直通**属性（当前只占位，宏注释写明"解析/降级留待将来"）；
- 库侧有**对齐用例矩阵** `rewrite::alignment_case_matrix_for_descriptor_lowering`（正例/边界/负例/安全区同源），
  将来宏降级出的描述符**直接拿它比对**，**无需在宏里写第二份语义**；
- 进度与未落地项如实记在 `docs/dev.md` §9.5.2（"宏 crate 集成未做"）。

## 5. 已实测的事实（引用，不改写）

> 口径与全部原始数据见点名的出处；本节**只做引用**，改数字请改出处。

| 事实 | 读数 | 出处 |
|---|---|---|
| **惯用 Rust**（迭代器 / 定长数组）vs 手写 LASX | 核 **1.48×（68%）**、组合步 **1.09×（92%）** | `docs/dev.md` §9.5.4 |
| **朴素索引循环** vs 手写 LASX | 核 **6.24×**、组合步 **3.20×** | `docs/dev.md` §9.5.4 |

| **形状机制变体**（锁步宽度 `L∈{2,4,8,16}`，f64） | `L=4` **0.99×（−1.3%）**、`L=2` 1.16×、`L=8` 5.82×、`L=16` 19.01×（手写 LASX 基准 0.1934 ms）⇒ **无变体达"快 ≥3%"门槛**；四宽度同手写逐位一致 | `docs/dev.md` §4 |

**诚实结论（本节的落点）**：

> **DSL 生成的代码可以超过"人手写的应用代码"，很难超过"专家手写的微内核"。**
>
> - 前者超得过，是因为 DSL 把**专家技巧变成默认**：等距递推、面板/计划复用、形状进类型带来的
>   编译期校验（`docs/ops.md` §9.10.1、`docs/dev.md` §7.10）——但**"形状"本身只够逼近**（§5.1）；
> - 后者超不过，是因为**微内核的 48% 差距来自 LLVM 做不到的结构**（散射写 + 行内串行递推，
>   实测只剩 68%）⇒ 架构上把"结构重写"做厚、把手写内核当**降级目标库**
>   （`docs/dev.md` §9.5.3 ③、§9.5.4 ③）。
>
> ⇒ **不要承诺"用宏就比手写快"**；承诺的是"**免费拿到**同一算法"（措辞见 `docs/dev.md` §9.5.1 的
> "诚实的优势定义"）。

### 5.1 能超越手写的条件：形状只能逼近，超越要靠算法/结构机制

**新实测（锁步宽度扫描，`docs/dev.md` §4）**：把"惯用定长数组"的锁步宽度 `L` 从 2 扫到 16
（f64、无 `mul_add`、同源、7 轮中位），最好的那一格 `L=4` 只到 **0.99×（−1.3%，在噪声内视为持平）**，
**没有任何变体达到"快 ≥3%"的超越门槛**，而且 `L=8/16` 迅速崩坏（5.82×/19.01×）——
机制是**寄存器压力**：状态/常数数组超出可用向量寄存器后溢出到栈，"跨行向量化"退化成标量内存往返；
`L=4` 恰好匹配 `F64x4`（256 位）且不溢出 ⇒ 与手写持平。四个宽度都与手写**逐位一致**（§4 的 E9）。

⇒ **把上面两条合起来，得到"能超越手写的条件"**：

1. **只改"形状/展开方式"（谁跟谁交错、多宽、什么顺序）⇒ 上限就是持平**：因为这属于"手写者早就
   已经手算过的最优形状"，宏只是把它自动化（收益是**免费拿到**，不是**超越**）。
2. **要"超越"，必须换机制**：用**算法/结构性质**把工作量降下来——例如**均匀网格 ⇒ Toeplitz
   ⇒ 卷积/FFT 的渐近收益**（把 `O(J·N)` 的核构造 + `O(J·N·NB)` 的矩阵乘换成更低阶的结构），
   或者利用对称性/稀疏性/可分离性做**因子分解**。这类收益**改变算术量**，不是重排既有算术。
3. **纪律不变**：换机制 = 换等价类 ⇒ 必须按 §2.2 登记（等价类 + 守卫/回退 + 认不出就不改写）；
   Toeplitz/FFT 这条路目前正是 §4 的**待定项 T1/T2**（下降形态与等价类未裁决）。
4. **`objdump` 待办**：`L=4` 的"持平"与 `L=8/16` 的崩溃与溢出解释一致，但"真的向量化了没有"的
   **逐指令佐证本轮未贴**（如实标未做，`docs/dev.md` §4）。

## 6. 第 1 层缺口清单与语法/类型草案

### 6.1 缺口清单

| 缺什么 | 解锁 | 现状依据（清点实测，不是推断） |
|---|---|---|
| `sum!`（单操作数归约） | `sum` 算子的声明式写法 | `docs/dev.md` §19.13 的 G1 行；宏层清点的 3.2 节 B2（探针 `dot!(x[K])` ⇒「缺少 `* 操作数`」）；库侧清点的 4.2 节 B2（`api::sum` 只吃裸 `&[f32]`） |
| `exp!` / `sin!` / `cos!`（**类型化逐元素**） | 核构造、激活函数、RoPE 类逐元素的声明式写法 | `docs/dev.md` §19.13 的 G2 行；核构造在本场景占整条 62–77%（`docs/ops.md` §9.10）；宏层清点的 3.1 节 A1–A5（探针 `lasx_rs::exp!(x)` ⇒ `E0433`）；库侧清点的 4.1 节 A1–A5 |
| `sum_range!` / `integral!`（**索引空间 / 迭代构造**） | `sum`、积分与带权求和的声明式写法；`laplace!`/`fourier!` 的下降目标 | 本文 §2.1；库内已走通的等价路径见 `docs/ops.md` §9.0；宏层清点的 3.2 节 B1–B5；库侧清点的 4.2 节 B1–B4 |

**共同点**：现有 DSL 的操作数**必须是缓冲**（`x[M, K]`），宏只能表达"两个缓冲的一次乘积"；
上面三类缺口的本质是**缺语法原语**，不是"缺 24 个宏"（`docs/dev.md` §19.13 的结论）。

### 6.2 草案：类型化逐元素（`exp!` / `sin!` / `cos!`）

**形状怎么进类型**：沿用已有的形状层向量类型（`shape::vec::VecRef<'_, T, N>` / `VecBuf<T, N>`，
`N` 是 const 泛型），风格与复数表面 `cmatmul::CMat<R, C>`（`docs/ops.md` §9.07）一致。

```rust
// 库侧类型化内建 = 正式入口（形状进类型、用户点名调用、库内 plan()/guard 自动选路）
let x = VecRef::<f32, { N }>::new(&buf)?;     // 已有类型
let mut y = VecBuf::<f32, { N }>::new();      // 已有类型
exp_into(&x, &mut y);                         // 目标：库内内建（形状由类型定）

// 宏糖（可选，遵守 §3：只转发）：两侧下标同名 ⇒ 逐元素
exp!(y[N] = x[N]);
```

- **"逐元素"的约束由下标同名表达**（与 `dot!` 的"两侧同长"共用同一条规则，`docs/dev.md` §19.13）；
  `N` 是 const 泛型 ⇒ 形状不匹配是**编译错误**。
- **标量参数**（`silu` 的 `a`、`gelu` 的近似档）作运行期实参，不进类型；需要"档位进类型"时用
  ZST 参数（`y = silu::<Exact>(&x)` 这类），以免一个宏长出多个版本。
- **与 `matmul!` 的衔接**：核矩阵就是行主序 `&[T]`，与 `Mat<R, C>` / `MatBuf` **同一存储布局**；
  `exp!` 写出的 `K[R, C]` 可以直接当 `matmul!` 的操作数（`matmul!` 不关心它怎么算出来的）。
  ⇒ **逐元素层不需要新的衔接机制**，只要"同一布局"这一条（现状已满足）。
- **仍缺的是"取值范围"**：类型里有形状、**没有数值范围**（`docs/dev.md` §9.5）⇒
  "编译期按范围选表/选阶"必须先有**显式范围声明**；在拿到真实用户场景前**不做**
  （范围注解草案见 `docs/dev.md` §9.5，本文不重复）。
- **落点（库侧清点的 L1/L2/L4，见 §6.5）**：`src/shape/elem.rs` 的类型化视图 + `src/api.rs` 的
  `exp`/`exp_into` 薄包装（后端复用现成的 `ops::nn_math::{exp_seq, exp_vec}`）。
  **一条口径要写死**（清点的 §5 第 4 条）：**决定代码生成/形状/调度的进类型；决定数值路线且
  需要显式 opt-in 的进显式值参数**——所以"精度路线（libm / 表 / 递推）"应当是**显式值**
  （对齐 `Route`），不要照 `Policy` 做成类型，否则会像现在 `Route`/`Weighting` 与 `Policy` 那样并存两套。
- **`sin`/`cos` 的位精确边界要写明**：库里 `exp` 有**位精确 f32 实现**（`ops::nn_math`，现为 `pub(crate)`），
  而 `sin`/`cos` **没有库内实现**（只在 `rope` 的表生成里走平台 libm，且表生成本身**不在位精确承诺内**，
  `docs/ops.md` §2.5 的例外口径）⇒ 新入口要么显式标"非位精确"，要么先补位精确后端
  （库侧清点的 3.3 / 4.1 节 A2）。

### 6.3 草案：索引空间 / 迭代构造（`sum_range!` / `integral!`）

**现状缺口**：没有"对索引 `i` 求和"的表达 ⇒ `sum` 与积分都写不出来（§6.1）。
草案用**一个**索引空间原语覆盖两者：

```rust
// 标量归约（解锁 sum!）
sum_range!(s = Σ_{i = 0..N} x[i]);

// 带权求和（梯形/Simpson）：输出维 j 写在左侧，收缩维 i 是求和索引
integral!(F[j] = ∫_0^T f(t_i)·k(θ_j·t_i) dt);
```

- **索引空间必须是 const 边界**（`0..N` 里的 `N` 是 const 泛型；运行期长度另走小写下标档，
  与 `matmul!` 的"大写=const / 小写=运行期"同规，`docs/dev.md` §19.8）。
- **步长有个硬约束**：**Rust 不允许 `f64` 作 const 泛型参数**，而索引步长天然是 `f64`
  ⇒ 若要"索引空间进类型"，步长必须表示成**有理数对**（`STEP_NUM/STEP_DEN`）或整数化
  （宏层清点的 3.2 节 B4；库侧落点见本文 §6.5 的 L7/L8）。
  现有载体是运行期字段 `StepKind::Literal(f64)`（`src/rewrite.rs`），**不能**直接当类型参数。
- **`integral!` 与库内 `laplace_batch_*` 的关系要先定**：两者**语义重叠**（后者已经是"核矩阵 + 两条
  实乘"），新语法要么**吃下它**、要么**明确切开**——别两处都叫"积分"
  （宏层清点的 5 节 b3）。
- **形状怎么进类型**：输出形状由**左侧下标**定（`F[j]` ⇒ `VecBuf<T, {J}>`），被求和项的形状由
  右侧定（`MatBuf<T, {J}, {NB}>`）；两侧的下标名必须一致（与现有"同一维必须写同一个下标"同一条规则）。
- **权重与步长**：`dt`、`w_i` 是运行期标量（或 const 字面量）；`Simpson` 的"整段回退梯形"这类
  回退规则属于 §2.2 的守卫，**必须把"是否回退"返回给调用方**（`laplace_batch_*_with` 的第二个
  返回值是既有形态，`docs/ops.md` §9.0）。
- **与 `matmul!` 的衔接（关键一步）**：当被求和项**可分离**——`w_i·k(θ_j·t_i)` 能写成
  "第 `j` 行一个参数 × 第 `i` 列一个参数"的**核矩阵**——时，`integral!` 的下降形态**就是**
  "先逐元素生成核矩阵 `K[J, N]`，再 `matmul!(F[J, NB] = K[J, N] * f[N, NB])`"。
  这正是库内 `laplace_batch_*` 已经走通的两条实乘（`docs/ops.md` §9.0），
  也是**为什么 `integral!` 在原语层、`laplace!` 在变换层**：后者只负责把 `e^{−st}`/`e^{−iωt}`
  认出来并选核、选路（libm / opt-in 递推）。
- **不可分离时**：不降级（报"无法降到矩阵乘"），**不猜**（§2.2 纪律 3）。

### 6.4 本阶段的铺垫顺序（建议）

1. **`exp!`/`sin!`/`cos!`（类型化逐元素）**：最小、无并行/计划问题，是核构造与激活的共同前置；
2. **`sum_range!`/`integral!`（索引空间）**：解锁 `sum!` 与积分，是 `laplace!`/`fourier!` 的下降目标；
3. **`laplace!`（第一个变换宏）**：把库内已实测的路径（两条实乘 + opt-in 递推）暴露成 DSL 语法，
   **判据与守卫全在库内**（§3）。

> 上面是**宏表面积**的顺序；**库侧先行的顺序**见 §6.6（清点建议：先 `Grid<N>` 与 `api::exp`，
> 再类型化视图，后通用化递推）。两者不冲突：库侧入口是宏能发射的前提（§3 的分工纪律）。

## 7. 红线"完全 SIMD"的定义：**红线 = A（2026-10-16 用户裁决）**

> **✅ 结论（用户决定，2026-10-16）**：**红线取 A** ——
> **引擎/可移植侧接受 rustc/LLVM 自动向量化也算 SIMD**，**判据 = 性能 + 可维护性**
> （不再要求"必须手写 intrinsic"）。
>
> **例外/定责（关键）**：**`lasx_rs` 是"专门后端"** ⇒ **其手写 intrinsic 保留、不删**
> （**A 是政策，不是删除令**）；但**它不再代表"库级无标量回退"** ——
> "全链路无标量回退 ＝ 完全 SIMD"**降级为 `lasx_rs` 这个后端自己的实现选择/局部保证**
> （`docs/ops.md §9.06` 已同步改措辞）。
>
> **理由（本仓实测，口径 `simd_dsl/docs/performance.md §5`）**：手写收益**只在"向量内核算子"上、且随形状放大** ——
> `lasx/idio`：**dot K=4096 `0.473×`（2.12×）**、**matmul 64³ `0.253×`（3.95×）**、
> **matmul 192×768×3072 `0.115×`（8.7×）**；而**核构造 `build_kernel_f32` `0.996×`（≈持平）**
> ⇒ **A 在引擎侧成立**。另两条支撑：**多累加器形状让 stable 档拿到 7.88×**（即 **intrinsic 的边际 ≈0**，
> 差距主要来自"形状/累加器数"而不是"手写"）；**loongarch64 默认特性下拿到的是 LSX 而非 LASX**，
> 而 **matmul 已被自动向量化吃满**（`bench.md §5.1` 的 `1.002×/0.998×` 口径）。
>
> **明确不变（逐条，一字不改）**：**位精确承诺**（`docs/ops.md §2.5`）、**`nm -D` = 98**、
> **默认路径行为**、**冻结接口清单**（`docs/dev.md` 的冻结小节）、**CI 十四步全绿**、**三端同步纪律**。
>
> **影响面**：**只改措辞与定级，不动一行代码、不删任何 intrinsic**。
> 完整决策记录见 `docs/dev.md §9.5.6`。

**背景（当时的论证，保留为历史）**：实测"惯用 Rust 到手写 LASX = **92%**，而且两者**逐位一致**"
（`docs/dev.md` §9.5.4）。于是出现一个**只能由用户定**的问题：**"完全 SIMD"这句话到底要求什么？**

**选项 A：接受"rustc/LLVM 自动向量化也算 SIMD"**

> **✅ 已裁决（2026-10-16，用户）**：**红线取 A**（以**性能与可维护性**为准），
> 但**明确 `lasx_rs` 作为"专门后端"的手写 intrinsic 保留、不删**（**A 是政策，不是删除令**）⇒
> 本节的 A/B 之争**已有结论**：**A 对引擎/可移植侧生效；B 在 `lasx_rs` 内部继续有效**。
> 详见 `docs/dev.md §9.5.6`（决策记录，含四行实测依据与"不变的项"）。
> 下面的利弊**保留为当时的论证**，不再当作待决问题。

- 利：可以删掉一批手写 intrinsic（例如组合步 `combine::{sub_f32, add_f32, sub3_f32}` 这类
  92% 到位、逐位一致的原语）；DSL 的"宏观前端"定位更纯；维护面更小。
- 弊：**会作废一条已验收的用户契约**——"全链路无标量回退 / 完全 SIMD"，且这条契约有
  `objdump` 逐指令佐证（`docs/ops.md` §9.06）；实测**当前仍慢 8%**（两个负载窗口一致，
  不是噪声，`docs/dev.md` §9.5.4 ⑤）⇒ 按"必须证明不退化"的口径，**现在删就是退化**。

**选项 B：坚持"必须 LASX intrinsic"（现状）**

- 利：契约不动，"完全 SIMD"这句话**可逐指令验证**；性能不退化。
- 弊：保留手写维护面；而且**语义上**"无标量回退"不等于"更快"——组合步向量化实测只值
  **0.19%**（负结论，`docs/ops.md` §9.06）。

**本文当时的建议：维持 B**（**已被上面的用户裁决取代**：红线取 A，但 `lasx_rs` 专门后端保留手写），
把 A 作为**条件性**选项：**当且仅当**（a）低负载窗口复测达到 ≥1.00×、（b）
用户**重新界定**该契约（换成"性能优先、允许 rustc 自动向量化"）时，才在同一提交里
"改契约文本 + 删原语 + 更新 `objdump` 验收"。理由：这是一条**已验收的需求**，
**性能优化的边界是需求，不是测量值**（`docs/dev.md` §9.5.4 的决策样板）。
⇒ **注意**：裁决后 **`lasx_rs` 侧仍然"不删"**，所以"删原语"这条路**在本仓不启用**；
"改契约文本"这一步已按 A 完成（定级为后端局部保证）。

**与 §6 的关系（重要）**：这条红线的对象是**库内已有原语与组合步**；它**不阻塞**第 1 层缺口的补齐
——新增 `exp!`/`integral!` 这类宏不需要删任何手写内核，也不会改变默认路径。

### 8.1 `macros/src/**`：现有能力与限制

**入口只有 4 个**（清点开头的"基线"表 + `docs/dsl-macros-inventory.md` §1）：`matmul!`、`dot!`、`gemv!`、
`#[fast_trig]`（**属性宏，当前原样返回 `item`，是无操作占位**）。

**文法与三条键规则**（`docs/dsl-macros-inventory.md` §1.1）：

```text
公式   := 操作数 '=' 操作数 '*' 操作数
        | 操作数 '*' 操作数
操作数 := ident '[' ident ',' ident ']'
        | ident                          ← 只在乘积右侧：视为 Prepared plan
标量   := ident | 字面量                ← 可选前缀（alpha 融合入口），写在乘积最前面
```

1. **下标首字符分档**：大写 = 编译期 `const`、小写或 `_` = 运行期值（这是选 proc-macro 的第一条理由，
   `macro_rules!` 读不到 ident 文本）；
2. **角色由共享下标判**：`x[M,K]*w[K,N]` 与 `w[K,N]*x[M,K]` 都认，归一后生成同一段代码；
3. **同一维必须写同一个下标**：宏在展开期报**双锚定**错误。

**能表达 / 不能表达**（宏层清点的 1.1 / 1.2 / 2.2 节）：

- **能**：两下标乘积（`=` 可选）、一维 `dot!`/`gemv!`、**plan 形态**（右操作数不带方括号）、
  **`alpha` 标量前缀**（**单个 token**，走 `mul_scaled_into`/`apply_scaled_into` 一类融合入口）；
- **不能**：`beta`（原地累加）、`+` 多操作数、**表达式**（标量只能是单个 token ⇒ `(alpha + 1.0) * x[..]`
  被拒）、**一元句式**（`*` 两侧各要一个带下标操作数）、**单操作数归约**、**逗号分隔的表达式实参**、
  **下标表达式**（`x[M + 0, K]` 被拒）、**跨语句依赖**。

**形状怎么进类型**（宏层清点的 1.3 节）：全部是 Rust **const 泛型**（**没有 `typenum`**）：

| 类型 | 形状在哪 |
|---|---|
| `Mat<'a, T, const R, const C>` / `MatBuf<T, const R, const C>` | R、C 全在类型里 |
| `MatDyn<'a, T, const C>` / `MatBufDyn<T, const C>` | 列进类型，**行是运行期字段** |
| `VecRef<'a, T, const N>` / `VecBuf<T, const N>` | 长度 `N` |
| `F16Vec<'a, const N>` / `F16Mat<'a, const N, const K>` | 长度/形状（元素固定为 `u16` 位型） |
| batch（`V3Ref`/`V3Buf`/`RvMut`/`V2Ref` + `*Dyn`） | SOA 批量样本维 |
| `CMat`/`CMat64`/`CMatBuf*` | 复数矩阵——**在 `ops` 层，不在 `shape` 层** |

派生量在 **const 求值**里算完（`Layout<K, N>` 的条带/面板/列尾/k 分块/打包字节），并有编译期自检
（`const _: () = assert!(…)`，不满足就编译不过）。dtype 面：`matmul!` 只覆盖 **f32/f64**；
`alpha` 系列**只 f32**；复数走独立的 `CMat` 手写路径，**DSL 不覆盖**。

**编译期检查靠四种机制**（宏层清点的 1.4 节）：**类型系统（主）**、**宏自己的名字层检查**、**DYN 档运行期断言**、
**`on_unimplemented`**（不支持的 dtype 对给可读提示）；`compile_fail` doctest **全仓只有一处**
（复数矩阵乘形状不匹配）。**两条必须点名的"守不住"**：

1. **"大写下标必须是 const"宏守不了**：proc-macro **没有名字解析**，`M` 是不是 const 要等 rustc
   （报 `cannot find value 'M' in this scope`）——这条只能写在文档里；
2. **负面诊断没有自动化验收**：仓库**有意不引 `trybuild`**（与"零第三方依赖"冲突），负面路径靠
   **人工核对编译输出**；宏规则层能单测是因为被拆成了**纯函数**。

**第 1 层缺口的实测证据**（宏层清点的 3.1 / 3.2 节；探针输出见该文件附录 A）：

| 组 | 缺口（逐条实测，不是推断） |
|---|---|
| **(a) 类型化逐元素** | **A1** 入口不存在（探针 `lasx_rs::exp!(x)` ⇒ `error[E0433]`）；**A2** 现有文法容不下一元（`*` 是必需的）；**A3** **库侧也没有可发射的逐元素面**（`VecRef`/`VecBuf` 只有 `new/len/is_empty/as_slice`；唯一按 dtype 分派的 trait 是给点积用的 `DotPair`）；**A4** 参数/标量只能一个 token；**A5** 取值范围不在类型里 |
| **(b) 索引空间 / 归约** | **B1** 下标只能是**裸标识符**（`x[M + 0, K]` 被拒）；**B2** 没有单操作数归约句式（`dot!(x[K])` 被拒）；**B3** 没有"逗号分隔的表达式实参"解析（`sum_range!(f, 0..N)` 无处落点）；**B4** 没有索引空间的类型级载体（蓝图是 `Layout` 的 const-eval，但 **`f64` 不能作 const 泛型** ⇒ 步长必须是有理数对或整数化）；**B5** 跨语句依赖无法表达 |

**依赖环（已确认**；宏层清点的 4 节）：`macros/Cargo.toml` 的 `[dependencies]` **为空**（无 `syn`/`quote`，
**也没有 `lasx_rs`**；也没有 `[dev-dependencies]`），而 `src/lib.rs` 反向 re-export 宏
⇒ **依赖环是硬的**：宏**不能在展开期**调用 `rewrite::plan()`/`recurrence_safe()`（连名字都取不到），
也不能 `use` 库内类型（如 `KernelPattern`）。宏**能**做的是把**描述符/调用发射进生成代码**
（先例：`dot!`/`gemv!` 发射绝对路径）。⇒ **推论（与 §3 同）**：宏层的产出只能是**代码 + 描述符**，
不能是**判定**；凡"编译期分析"型结论（范围、安全区、快慢路径）都必须以"库内函数 + 生成代码调用"落地。
（清点另给了次要理由：proc-macro 依赖按**宿主**目标编译，而本库是 loongarch64-only ⇒ 即便无环也不该拖进来。）

**最小路径与量级**（宏层清点的 5 节）：见本文 §6.6（a1–a3 / b1–b3）。

**规范化要点**（宏层清点的 6 节，供后续整顿）：宏名沿用"**小写算子名 + `!`**"（宏层清点的 6.1 节的 N5；
不要用 `apply!` 当唯一入口）；
**生成代码卫生统一走绝对路径**（现在 `matmul!` 发射裸类型名、`dot!`/`gemv!` 发射绝对路径 ⇒ 是否要 `use`
不一致）；新原语的**规则层要拆成纯函数**才能单测，Span 层靠 example 编译核对；**"谁守"逐条点名**；
负面路径用 **`compile_fail` doctest**、**不引 `trybuild`**；诊断建议给稳定**类别码**（少抄文案）。

### 8.2 Rust 侧类型化面：现状与缺口

**形状进类型的现有载体**（库侧清点的 1 节）：`Layout<const K, const N>`（派生量全在
const 求值 + `const _: () = assert!` 自检）、`Mat`/`MatBuf`（两个 const 参数）、`MatDyn`/`MatBufDyn`
（列进类型、行是运行期字段）、`Prepared<P, T, K, N>`（内部持一个 `MatmulPlan`，`apply*` 零分配、零重打包）。
**构造时只查长度**，形状匹配由 const 参数强制（写错就是 `E0308`）；`Policy` 是**零尺寸类型上的纯判据**
（`Auto` / `Single` / `Exact<N>`，不建池、不派活）。

**类型化样板 `CMat`**（库侧清点的 2 节）：`CMat<'a, R, C>` / `CMatBuf<R, C>` + `mul_into<const N>`——形状全靠三个 const
参数对齐；**编译期保证用 `compile_fail` doctest 作证**（全仓唯一一处），而 `shape::Mat` **缺这一条**。
**样板自身有两处裂缝**：① `CMat::new -> Option` 丢掉了 `op/what/expected/got`（与 `Mat::new -> Result`
不一致）；② 数值路线 `Route` 是**运行期枚举**，而 `Policy` 是**类型**——第 1 层落地前必须选一边
（本文 §6.2 的口径：**选值**）。

**`api::*` 与 `_into` 约定**（库侧清点的 3 节）：统一形如 `<name>_into(<inputs…>, out: &mut [T]) -> Result<()>`，共 **24 个**；
**`matmul`/`matmul_f64` 没有 `_into`**（只有 `matmul_scaled_into`），另有一处返回 `Result<f32>` 的例外。
**逐元素现状**：公开的只有就地 `axpy` 与 `silu`/`gelu_*`；`ops` 里的逐元素原语是 `pub(crate)`；
**`exp` 有位精确 f32 实现**（`ops::nn_math::{exp_seq, exp_vec}`）但**不可达**；**`sin`/`cos` 没有库内实现**
（只在 `rope` 的**表生成**里走平台 libm，且**表生成本身不在位精确承诺内**）。
⇒ 缺口不只是"宏没有语法"：**库侧也缺两个"类型化的域"**（逐元素视图、索引空间），见库侧清点的 4.1 / 4.2 节。

**可复用的现成件（不要重写**；库侧清点的 4.3 节）：`ops::nn_math::{exp_seq, exp_vec}`（位精确 f32 `exp` 后端）、
`ops::sum`（归约后端）、`laplace::{Weighting, trapezoid_weights, recurrence_safe, RECURRENCE_MAX_PHASE*}`
（求积权重 + 同源安全区守卫）、`laplace_batch_*_recurrence`（递推 + 逐行回退 libm 的行为链路）、
`rewrite::{KernelPattern, plan, safe, safe_zone}`（纯函数判据，**接新类型的天然接口**）、
`fast_trig::{fast_exp, fast_cos_sin}`（非位精确后端）、`Policy`/`Exact<N>`（策略进类型的范式）、
`V2Ref::distance2d_into`（**"类型化层不返回 `Result`"**的先例）。

**规范化建议**（库侧清点的 5 节，摘要）：构造失败统一 `Result<Self, Error>`；补齐 `matmul(_f64)_into` 空洞；
`combine::*` 的"`out.len()` 驱动 + `assert!`"要么加 `Result`、要么显式降为 `pub(crate)`
（**不能保持"pub 且 panic"**）；**写死分层口径**——"决定代码生成/形状/调度的进类型；
决定数值路线且需要显式 opt-in 的进显式值参数"；"谁守"逐条点名；补齐 `compile_fail` doctest；
命名与访问器统一（`<View>`/`<View>Buf`、`new()`、`*_into`）。

**落点建议 L1–L12、落地顺序与完成判据**：见本文 **§6.5 / §6.6**（已并入）。
